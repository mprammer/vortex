# ffi-boundary-bench (experiment E4)

Quantifies the cost of crossing the Rust↔host-runtime boundary when reading Vortex,
to support the "no hot-path penalty" claim in the *Vortex as an Iceberg file format* proposal.

## What it measures

All three Vortex bindings hand Arrow off across the language boundary via the **Arrow C Data
Interface** (a C-stream of `ArrowArray`/`ArrowSchema` structs), so buffers are *shared, not
copied*. This benchmark does not test *whether* a copy happens — by construction it does not — it
**quantifies the per-batch import overhead** and shows it is flat per *batch*, not per *row*.

Three paths read the **same** Vortex file and run the **same** trivial consume workload
(sum one `f64` column + count rows, to force full materialization):

| Path | Boundary | How it reads |
| --- | --- | --- |
| **native** | none (control) | `VortexFile::scan().into_record_batch_stream()` in-process |
| **jvm** | Rust→JVM via `vortex-jni` | `DataSource.open(...).scan(...)` → `Partition.scanArrow()` → Arrow `ArrowReader` (C Data Interface) |
| **python** | Rust→CPython via PyO3 | `vortex.open(path).to_arrow()` → `pyarrow.RecordBatchReader` (C stream) |

`native` is the floor; `jvm`/`python` minus `native` is the boundary overhead.

## Method

- **Input**: a synthetic Vortex file generated by `ffi-boundary-bench gen` (columns: `id` i64,
  `value` f64, `category` utf8), so all three runtimes read identical data. Plain encodings keep
  decode cost comparable and isolate the boundary.
- **Sweep batch size** (rows-per-batch) at fixed total rows: if overhead is per-batch, total
  boundary cost should scale with batch *count*, not row count. Report ns/batch and rows/s.
- **Warmup**: discard the first K iterations (JVM JIT, page cache); report steady-state p50/p95.
- **Metrics**: wall time, rows/s, ns/batch, batch count.

## Acceptance (what makes the claim defensible)

- `jvm`/`python` throughput within **a few %** of `native` at realistic batch sizes (≥ 8k rows).
- Boundary overhead **O(batches), not O(rows)**: doubling rows-per-batch (halving batch count)
  roughly halves total boundary cost.
- No per-row marshalling: the only per-batch work is exporting/importing the C Data Interface
  structs (pointers + schema), never buffer copies.

## Running

All three over one shared file, with a Mrows/s comparison:

```bash
FILE=/tmp/boundary.vortex ROWS=5000000 bash benchmarks/ffi-boundary-bench/run_all.sh
```

Or individually:

```bash
# 1. generate the shared input (native runner owns data-gen)
cargo run -p ffi-boundary-bench --release -- gen --rows 5000000 --out /tmp/boundary.vortex

# 2. native baseline
cargo run -p ffi-boundary-bench --release -- bench --file /tmp/boundary.vortex --iters 12 --warmup 4

# 3. python (PyO3) — needs the vortex-data wheel
uv run --reinstall-package vortex-data python \
  benchmarks/ffi-boundary-bench/runners/python_runner.py --file /tmp/boundary.vortex

# 4. jvm (vortex-jni) — downloads a JDK 17 toolchain on first run
cd java && JAVA_HOME=/opt/homebrew/opt/openjdk/libexec/openjdk.jdk/Contents/Home \
  BOUNDARY_VORTEX_FILE=/tmp/boundary.vortex BOUNDARY_OUT=/tmp/jvm.txt \
  ./gradlew :vortex-jni:test --tests 'dev.vortex.api.BoundaryBench' -i
```
